# 登录注册与认证功能实现思路

## 1. 功能目标

认证功能用于保护设计工作台入口，并为按用户保存设计、订单和素材提供用户身份基础。账号生命周期、会话校验和设计草稿的用户归属已经完成；订单历史和独立素材存储仍可继续扩展。

## 2. 前端流程

应用启动时先读取浏览器中的访问令牌：

1. 没有 token 时显示登录页。
2. 有 token 时进入 `checking` 状态，请求 `/api/auth/me`。
3. 校验成功后进入设计编辑器，并把当前用户传给顶栏。
4. 校验失败则清理 token，回到登录页。

登录页调用 `POST /api/auth/login`。勾选“保持登录”时将 token 写入 `localStorage`，否则写入 `sessionStorage`。注册页调用 `POST /api/auth/register`，成功后回到登录页并预填用户名。退出登录调用 `POST /api/auth/logout`，无论后端响应如何都清理本地 token。

认证请求由 `frontend/src/api.js` 统一封装：自动添加 `Authorization: Bearer <token>`，统一解析 401、403、409、503 和参数校验错误，并把后端错误转成用户可读提示。

## 3. 后端分层

- `routes/auth.py`：提供注册、登录、当前用户和退出登录接口。
- `schemas/auth.py`：定义请求和响应结构，注册密码最少 8 位。
- `services/auth_service.py`：编排用户名规范化、重复账号检查、密码哈希、登录校验、会话写入和最后登录时间更新。
- `crud/users.py`：封装用户查询、创建和最后登录时间更新。
- `models/users.py`：映射用户表，包含用户名、密码哈希、职位、启用状态和最后登录时间。
- `core/security.py`：使用推荐密码哈希算法，并生成带 `sub`、`sid`、`iat`、`exp` 的 JWT。
- `api/dependencies/auth.py`：解析 Bearer token，校验 JWT、Redis 中的会话 ID 和用户状态。

## 4. 会话模型

登录成功后同时生成 JWT 和随机 `session_id`。JWT 负责携带用户 ID 和过期时间，Redis 以用户 ID 保存当前会话 ID。每次访问受保护接口时，后端必须同时满足：JWT 签名和有效期正确、JWT 中的 `sid` 与 Redis 值一致、用户存在且处于启用状态。这样可以通过删除 Redis 会话立即使 token 失效，并限制同一账号的当前有效会话。

默认访问令牌有效期为 60 分钟，Redis 会话默认保留 7 天，实际值由环境变量覆盖。生产环境必须设置独立且安全的 `JWT_SECRET_KEY`、数据库和 Redis 配置，不能使用开发默认密码。

## 5. 错误和安全边界

- 用户名在服务端统一清理和规范化，重复用户名返回 409。
- 密码只保存哈希，不保存明文；登录失败不暴露账号是否存在。
- 停用账号返回 403；缺少、过期或被替换的会话返回 401。
- Redis 不可用时登录和退出登录会明确提示认证服务不可用，避免产生“看似登录成功但会话无法校验”的状态。
- CORS 由 `CORS_ORIGINS` 配置，前端开发端口已加入默认允许列表。

## 6. 与设计数据的关系

设计数据现在已与登录用户绑定。前端 `designStore` 在编辑时保留内存状态，并通过防抖调用 `PUT /api/designs/{template_id}`；后端将完整设计 JSON 保存到 PostgreSQL 的 `design_drafts` 表，同时写入 Redis 缓存。读取时使用 `GET /api/designs/{template_id}`，先查 Redis，未命中再查询 PostgreSQL 并回填缓存。

浏览器 `localStorage` 仍保留为网络异常时的兜底，不再是登录用户的主数据源。下一阶段可继续拆分：

- 设计草稿历史版本和订单接口；
- 服务端独立保存模板版本、裁片元素和素材元数据；
- 上传素材的对象存储或受控文件服务；
- 登录用户只能读取和修改自己的设计；
- token 过期后的刷新或重新登录策略。

## 7. 当前未实现的认证扩展

- 忘记密码、邮件或验证码找回。
- 邮箱验证和多因素认证。
- 多设备会话列表与主动踢出指定设备。
- 角色/权限控制和管理员用户管理。
