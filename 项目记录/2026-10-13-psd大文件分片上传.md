# 2026-10-13 PSD 大文件分片上传实现记录

## 背景

设计工具面向裁剪定制，原始 PSD 源文件可达数百 MB（上限按 500MB 设计）。此前后端 RustFS 对象存储仅支持 ≤25MB 的小图片（`RUSTFS_MAX_UPLOAD_BYTES`），无法承接大体积 PSD。本次新增一套 **分片可续传上传协议**：客户端把文件切片、并发多线程上传，后端用 **S3 Multipart Upload** 编排，最终合并为完整对象。前端配套可复用分片上传客户端与进度条 UI。

## 协议设计（后端 /api/psd）

| 方法与路径 | 作用 |
|---|---|
| `POST /api/psd/uploads` | 创建上传会话：校验 `.psd` 类型与 `size ≤ 500MB`，算好 `part_size`（夹紧到 S3 5MB 下限）/`total_parts`，开启 RustFS multipart，会话存 Redis |
| `PUT /api/psd/uploads/{sid}/parts/{n}` | 上传第 n 个分片（请求体为原始字节）。可被前端**并发调用**，S3 允许乱序 part |
| `GET /api/psd/uploads/{sid}` | 查询已完成分片 → 前端断点续传 |
| `POST /api/psd/uploads/{sid}/complete` | 校验 1..total 全齐后合并，返回 `object_key/etag/预签名url`，清理会话 |
| `DELETE /api/psd/uploads/{sid}` | 中止，删除已传分片并清理会话 |

## 关键实现点

- **多线程来自客户端并发请求**：前端开一个 worker 池并发打多个 part 请求，uvicorn 各自处理，boto3 经 `anyio.to_thread.run_sync` 在线程池执行，无需额外服务端并发配置。
- **切分参数**：`part_size = clamp(请求值或默认 8MB, S3 下限 5MB, 文件大小)`；`total_parts = ceil(size/part_size)`，超 S3 10000 片上限时自动放大分片。示例：500MB / 8MB ≈ 63 片。
- **会话状态存 Redis**：键 `{REDIS_KEY_PREFIX}:psd:session:{sid}`，记录已传分片（PartNumber→ETag），TTL 24h；complete/abort 后删除，避免孤儿 multipart。
- **安全**：对象键作用域 `users/{uid}/designs/{order}/psd/{uuid}.psd`；会话记录 `owner_user_id` 防越权；服务端强校验分片范围、单片大小、complete 前分片是否齐备、文件名 `.psd` 后缀。
- **错误映射**：`PsdUploadError` 统一转 HTTP（413 超限/超大、415 非 PSD、404 会话不存在、403 越权、503 RustFS/Redis 不可用；`NoSuchUpload` 归为 404）。

## 前端集成

- `frontend/src/psdUpload.js`：可复用控制器 `uploadPsdFile()` — `file.slice()` 切片、4 路并发 worker 池、单片失败自动重试 3 次、进度回调、支持传入既有 `sessionId` 断点续传、失败兜底 abort。
- `frontend/src/api.js`：新增 `initPsdUpload / uploadPsdPartRaw / getPsdUploadStatus / completePsdUpload / abortPsdUpload`；分片用原始 `fetch`+鉴权头（body 是字节，不走 JSON 封装）。
- `frontend/src/components/PsdUploadDialog.jsx`：居中进度条弹窗（上传中 / 完成 / 失败三态）。
- 编辑器顶部 Header 新增“导入 PSD”按钮，触发隐藏 file input，调用 `uploadPsdFile`，实时显示分片进度与最终 object_key。

## 当前边界与待完善

- PSD 上传成功仅返回 RustFS 对象引用（object_key/预签名 url），**尚未挂到设计草稿/素材清单**当中；如何承载“一个设计对应一个或多个 PSD 源文件”的关联关系待定。
- 前端进度弹窗上传中不允许关闭；未接入真正的“中断后从上次进度续传”持久化（`sessionId` 未写入 localStorage，断点续传能力在控制器层已具备）。
- 会话过期/僵尸 multipart 仅靠 Redis TTL + complete/abort 清理，尚无后台定时扫描 `list_multipart_uploads` 的兜底清理任务。
- 分片上传粒度固定为单次 PUT 一个 part，未引入 boto3 `TransferConfig` 的服务端多线程分片路径。
